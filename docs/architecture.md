# Azureジョブ実行基盤のアーキテクチャ比較
---

## 1. 本資料の目的

本資料は、オンプレミス環境からAzureへジョブ実行要求を送信するシステムについて、適切な実行アーキテクチャを検討するためのものである。

当初、Triggered WebJobsを利用する構成が検討されていたが、オンプレミスからの非同期・並列実行が要件どおりに実現できないとの問題が報告された。

これを受けて複数の代替案が検討され、MicrosoftからもDurable Functionsによる構成が提案されている。

本資料の目的は、特定の方式を採用することではない。

**各方式の機能、制約、実装負荷、障害復旧、運用負荷を比較し、業務要件に適した構成を技術的根拠に基づいて選択することである。**

特に以下を重視する。

- 当初案の問題を正しく理解する。
- Azureの標準機能で実現できる処理と、独自実装が必要な処理を区別する。
- 初期開発工数だけでなく、継続的な運用・保守コストも評価する。
- 技術選定の理由を第三者に説明できるようにする。

## 2. 現在判明している課題

### 2.1 Triggered WebJobsの問題

当初案では、Triggered WebJobsをオンプレミス環境から非同期・並列に実行できないことが課題として報告されている。

ただし、以下の3つは異なる要件である。

| 要件 | 意味 |
|---|---|
| 非同期起動 | 要求元がジョブ完了を待たずに処理を継続できる |
| 同時並列実行 | 複数のジョブが同じ時間帯に実行できる |
| スケールアウト | 複数の実行インスタンスに負荷を分散できる |

Triggered WebJobsはREST APIによる実行要求が可能であり、同時実行も一律に禁止されているわけではない。

一方、既定の実行モデルでは選択された単一のApp Serviceインスタンスで実行されるなどの制約がある。

そのため、「非同期・並列実行できない」という報告については、製品仕様による制約なのか、実装・構成に起因する制約なのかを確認する必要がある。

**なお、この原因究明を理由に代替案の検討を止める必要はない。両者は並行して進められる。**

### 2.2 今回の設計で実現したい処理

現時点で想定されている処理は次のとおりである。

1. オンプレミスからジョブ実行要求を受信する。
2. 必要な入力データをBlob Storageへ保存する。
3. Azure Batchへジョブまたはタスクを投入する。
4. 複数要求を非同期・並列に処理する。
5. Azure Batchの実行状態を確認する。
6. 完了後に結果を収集・集計する。
7. 異常発生時には、必要に応じて復旧・再実行する。

このうち、どの処理が必須要件で、どの処理が現在の実装方式に由来するものかを区別する。

## 3. 検討対象の5案

### 案1：App Service + 二段構成Azure Batch

App Serviceが要求受付とBlob格納を行い、別の管理用Azure Batchに投入・監視・集計処理を担当させる。

管理用Batchから、計算用Batchにジョブを投入する。

**主なメリット**
- 既存のジョブ管理プログラムを再利用できる可能性がある。
- 投入・監視処理をApp Serviceから分離できる。
- Azure Batchを中心に処理を構成できる。

**主な懸念**
- 管理用と計算用の二段構成になり、運用対象が増える。
- 管理用タスクの障害復旧と状態復元を検討する必要がある。
- 長時間の状態監視が、計算リソースを占有する可能性がある。
- ジョブの重複投入や中断後の再開方法を確認する必要がある。

**確認事項：管理用Batchの処理は既存資産をそのまま利用できるのか。それとも新規実装が必要なのか。**

### 案2：App Service集約

App Serviceで要求受付、ローカル保存、内部キュー、非同期スレッドによるAzure Batch投入・監視まで実施する。

**主なメリット**
- コンポーネント数が少ない。
- 比較的単純なプログラムとして構築できる可能性がある。

**主な懸念**
- App Serviceの再起動やスケール操作によって、バックグラウンド処理が中断される可能性がある。
- プロセス内部のキューだけでは、実行要求の確実な永続化が難しい。
- Webアプリとバックグラウンド処理がリソースを共有する。
- 自前の非同期スレッドは、ホストのライフサイクル管理と整合させる必要がある。

ローカル保存や内部キューだけに依存する場合、障害後の復旧が難しくなるため、十分な検証が必要である。

### 案3：Queue Storage + Continuous WebJob

App ServiceがQueue Storageへ要求を登録し、同じApp Service Plan上のContinuous WebJobが要求を取り出してAzure Batchへ投入する。

**主なメリット**
- 要求受付とジョブ投入を分離できる。
- Queue Storageによって未処理要求を永続化できる。
- 既存のApp Service Planを利用できる可能性がある。
- 単純な非同期ジョブ処理と相性がよい。

**主な懸念**
- 投入後の監視や結果集計は別途実装が必要。
- WebJobとWebアプリが計算リソースを共有する。
- キューメッセージの再配信による重複処理を考慮する必要がある。
- 複数ワーカー間の排他・同時実行数を設計する必要がある。

### 案4：Queue Storage + Azure VM

App ServiceがBlobに入力を保存し、Queue Storageへ要求を登録する。

独立したAzure VM上の常駐プロセスがQueueを監視し、既存のHpcComコンポーネントを通じてAzure Batchへタスク投入する。

**主なメリット**
- HpcComなどの既存資産を再利用できる可能性がある。
- App Serviceとは独立して投入処理を実行できる。
- 実行環境の制御に自由度がある。

**主な懸念**
- VMのOS更新、監視、障害復旧が必要。
- 常駐プロセスの冗長化や再起動制御が必要。
- キューの状態と実際の投入結果の整合性を管理する必要がある。
- リソース使用率が低くてもVMの稼働コストが発生し得る。

### 案5：App Service + Durable Functions

App ServiceがBlobに入力を保存し、HTTP Triggerを通じてDurable Functionsを開始する。

OrchestratorがActivityを呼び出してAzure Batchへジョブを投入し、Durable Timerによって待機しながら、状態照会と結果集計を進める。

**主なメリット**
- ワークフローの進行状況と履歴を永続化できる。
- Durable Timerにより、待機中に実行スレッドを占有する必要がない。
- 処理途中からの復元をフレームワークが支援する。
- 複数の処理や依存関係をコード上で表現できる。
- 進捗確認や障害調査に利用できる仕組みがある。

**主な懸念**
- OrchestratorとActivityという実装モデルの理解が必要。
- 決定性やリプレイに関する制約がある。
- ワークフローのバージョン互換性を考慮する必要がある。
- Activityの重複実行対策は依然として必要。
- Durable Functionsと永続化バックエンドの利用料金・設定・運用が必要。

## 4. 5案の比較

以下は、機能の有無ではなく、**その機能を実現するためにどの程度の独自設計が必要か**を中心にした概略比較である。

| 評価項目 | 案1 二段Batch | 案2 App集約 | 案3 Queue+WebJob | 案4 Queue+VM | 案5 Durable |
|---|---|---|---|---|---|
| 非同期要求受付 | ○ | ○ | ◎ | ◎ | ◎ |
| 並列処理 | 構成次第 | 自前制御 | ワーカー制御 | ワーカー制御 | 標準機能で支援 |
| 受付要求の永続化 | 別途確認 | 別途設計 | Queue | Queue | Durable履歴 |
| 投入後の状態監視 | 管理タスク | App内部 | 別途実装 | 常駐処理 | Monitor Pattern |
| 長時間待機 | 実行タスク依存 | 実行プロセス依存 | 設計次第 | 常駐処理 | Durable Timer |
| 障害後の再開 | 独自設計 | 独自設計 | 独自設計 | 独自設計 | 標準機能で支援 |
| ジョブ二重投入防止 | 必要 | 必要 | 必要 | 必要 | 必要 |
| 業務上の状態遷移 | 独自実装 | 独自実装 | 独自実装 | 独自実装 | 独自実装 |
| 実行履歴の可視化 | Batch等 | 独自管理 | ログ等 | ログ等 | Durable Backend |
| 実行基盤の管理 | 管理用Batch | App Service | App Service | VM | Functions |
| 新しい設計モデルの学習 | 比較的小 | 小 | 小〜中 | 既存資産次第 | 中 |
| 初期開発工数 | 再利用率次第 | 要検証 | 要検証 | 再利用率次第 | 要検証 |

この表から一律に優劣を決めることはできない。

重要なのは、既存資産の再利用率と、独自実装が必要な処理の範囲である。

## 5. 追加で検討すべき方式

今回の主要要件が単純な非同期・並列処理であるなら、**Queue Storage + Queue Trigger Azure Functions**も比較する価値がある。

```text
App Service
    ↓
Queue Storage
    ↓
Queue Trigger Function
    ↓
Azure Batch
```

この方式では、要求の永続化、キューからの取得、並列実行、再試行などにAzureの標準機能を利用できる。

一方、Azure Batchへ投入した後の長時間監視や結果集計は別途設計する必要がある。

**ワークフロー管理が必要な場合はDurable Functions、単純なキュー処理なら通常のFunctions**という比較軸を持つと、過剰な構成を避けやすい。

## 6. Azure Batchの標準機能との責任分界

Azure Batchは、単に計算プログラムを起動するサービスではない。

タスク管理、実行状態管理、再試行、依存関係などの機能を備える。

例えば、複数タスクの完了後に後続タスクを実行する処理は、Batch Task Dependenciesを利用できる場合がある。

したがって、次の責任分界を検討する。

| 処理 | 主な担当候補 |
|---|---|
| 業務要求の受付 | App Service |
| 入力データ保存 | Blob Storage |
| 計算資源管理・タスク実行 | Azure Batch |
| Batch内部のタスク依存関係 | Azure Batch |
| 複数サービスにまたがる制御 | 必要ならDurable Functions |
| 状態照会・結果集計 | 業務要件に応じて選定 |

Azure Batch自身が管理できるものを、別の層で重複実装しないことが望ましい。

## 7. Durable Functionsを理解するための基本概念

Durable Functionsの特徴は、単に処理を起動することではなく、**途中までの進行状況を維持しながら、複数の処理を制御できること**である。

### 7.1 Orchestrator

どの処理をどの順番で実行するかを定義する。

例えば次のような処理である。

1. Azure Batchへジョブを投入する。
2. 状態確認のためのActivityを呼び出す。
3. 未完了ならDurable Timerで待機する。
4. 状態確認を繰り返す。
5. 完了したら結果集計を実行する。

### 7.2 Activity

実際の外部操作を実行する。

例えば、Azure Batch APIへのアクセス、ジョブ投入、Blobの読み書きなどが該当する。

### 7.3 Durable Timer

ワークフローを一定時間待機させる。

通常の長時間Sleepとは異なり、待機中に実行スレッドを占有し続ける必要がなく、実行履歴を使って再開できる。

### 7.4 Durable Task Scheduler

DTSは、Durable Functionsで利用できるマネージドバックエンドの一つである。

実行履歴の永続化やスケジューリングを担い、Dashboardで状態を確認できる。

ただし、Durable Functionsの永続化バックエンドはDTSだけではない。

また、DTSがAzure Batch上の計算処理を直接監視しているわけではなく、状態照会を行うActivityなどを通じて情報を取得する必要がある。

## 8. 関数型プログラミングの基本

Durable Functionsを実装する場合、関数型プログラミングの考え方が役立つ。

ただし、C#を関数型言語に置き換える必要はない。

### 8.1 純粋関数

純粋関数とは、同じ入力から同じ出力を返し、関数の外部に副作用を発生させない関数である。

```csharp
public static bool CanRetry(
    int retryCount,
    int maxRetries)
{
    return retryCount < maxRetries;
}
```

同じ引数なら同じ結果になる。

このような関数は、Azure Functionsを起動しなくても単体テストができる。

### 8.2 イミュータブルなデータ

作成済みのデータを直接変更するのではなく、新しいデータを返す。

```csharp
public record JobState(
    string JobId,
    int RetryCount,
    JobStatus Status
);
```

```csharp
public static JobState IncrementRetry(
    JobState state)
{
    return state with
    {
        RetryCount = state.RetryCount + 1
    };
}
```

これにより、意図しない状態変更を抑制できる。

### 8.3 状態遷移も純粋関数にできる

```csharp
public static JobState Complete(
    JobState state)
{
    return state with
    {
        Status = JobStatus.Completed
    };
}
```

この関数は既存の状態を書き換えず、新しい状態を計算して返す。

### 8.4 副作用を分離する

外部API呼び出し、DB更新、ファイル保存などは副作用を伴う。

Durable Functionsでは、これらをActivityへ分離することが基本となる。

考え方は次のとおりである。

**業務ルールを計算する処理と、外部システムを操作する処理を分ける。**

この設計により、業務ロジックをAzure Functionsから独立してテストしやすくなる。

### 8.5 OOPとの関係

関数型とOOPは対立するものではない。

外部サービスとの連携にはOOPやDIを利用し、業務ロジックには純粋関数を利用するといった使い分けが可能である。

重要なのはプログラミングパラダイムそのものではない。

**状態・副作用・依存関係の複雑性を局所化し、プログラムの振る舞いを理解・検証しやすくすることである。**

### 8.6 Orchestratorには決定性が必要

Durable Functionsは実行履歴をリプレイして処理を復元する。

そのため、Orchestratorでは同じ履歴から同じ実行判断を再現できる必要がある。

Orchestratorは厳密な意味の純粋関数ではないが、副作用を分離して決定的に実装することが重要である。

## 9. 実装工数の比較方法

初期開発工数だけを比較すると、既存資産を活用できる方式が有利になることがある。

しかし、以下の項目も含めて比較する必要がある。

| 項目 | 確認する内容 |
|---|---|
| 既存資産の再利用 | 変更なしで使える範囲 |
| 新規実装 | 本当に追加開発が必要な処理 |
| 状態管理 | 永続化・復元の実装が必要か |
| 障害復旧 | 二重投入や中断後の再開にどう対応するか |
| テスト | 正常系・異常系を検証しやすいか |
| 監視 | 障害原因をどこまで追跡できるか |
| 運用 | VMや管理プロセスの保守が必要か |
| 将来変更 | ジョブ数や処理手順の変更に対応しやすいか |

例えば、案1で既存の投入・監視プログラムをほぼ変更せずに利用でき、障害復旧要件も満たせるのであれば、合理的な選択肢となる。

一方、実際には大量の状態管理・例外処理・復旧機能を新規実装する必要があるなら、Durable Functionsを利用したほうが総工数を削減できる可能性がある。

どちらが優れているかは、実装内容を具体化しなければ判断できない。

## 10. PoCの検証方針

技術選定のためのPoCでは、すべての業務機能を実装する必要はない。

共通の最小シナリオを使って、各案の成立性と実装負荷を比較する。

**共通シナリオ**

1. 複数の実行要求を同時に受信する。
2. Azure Batchへ非同期でタスクを投入する。
3. タスクの実行状態を確認する。
4. 正常終了したら結果を集計する。
5. Azure側の実行コンポーネントを途中で停止する。
6. 再起動後、重複投入や処理消失なく継続できるか確認する。

### 重点検証項目

| 項目 | 評価内容 |
|---|---|
| 非同期受付 | 要求元が完了を待たずに処理を継続できる |
| 並列処理 | 想定する同時実行数を実現できる |
| 状態の追跡 | 要求から結果集計まで追跡できる |
| 障害復旧 | 再起動後に処理を再開できる |
| 冪等性 | 二重投入を防止できる |
| 実装量 | 必要な独自コードと設定の量 |
| 運用負荷 | 障害調査と復旧手順 |
| 性能・コスト | 想定負荷での処理性能と費用 |

PoCの結果は、実行ログ、構成図、ソースコード、テスト結果を残し、方式ごとの比較根拠とする。

特にMicrosoftから提案された案5については、最低限のジョブ投入・監視・完了処理を実装し、公式のMonitor Patternがどこまで利用できるか確認することが望ましい。

## 11. 技術選定の判断基準

以下は、最終判断のための基本的な考え方である。

**案1が有利になる条件**

- 既存の管理プログラムを高い割合で再利用できる。
- 管理タスクの状態・障害復旧をAzure Batchの機能と既存ロジックで十分管理できる。
- 二段構成による運用負荷が許容範囲である。

**案3・Queue Trigger Functionsが有利になる条件**

- 各ジョブが独立している。
- 主な要件が非同期受付とジョブ投入である。
- 複雑なワークフロー管理が不要である。

**案5が有利になる条件**

- 投入後の長時間監視が必要。
- 処理途中の状態を保持する必要がある。
- 複数処理の依存関係や再試行が必要。
- システム停止後もワークフローを再開したい。
- 独自の状態管理処理を減らせる。

どの方式でも、外部ジョブ投入の冪等性、実際のジョブ状態との整合性、必要な障害復旧は検討しなければならない。

## 12. 最終結論

今回の技術選定において、Durable Functionsの採用を前提とする必要はない。

既存資産を再利用できる第1案が最も合理的である可能性も十分にある。

しかし、技術選定では、採用する方式の利点だけでなく、他の選択肢を採用しない理由も説明できる必要がある。

**重要なのは、各方式の機能と制約を理解し、必要な実装と運用負荷を比較したうえで判断することである。**

Microsoftが提案したDurable Functionsについても、メリットがあると推測するだけでは不十分である。同様に、実装負荷が大きそうだという推測だけで候補から除外すべきでもない。

公式ドキュメントと小規模なPoCを利用して、その方式が要件に適合するか確認する。

その結果、Durable Functionsを採用しないという結論になっても、合理的な比較と検証に基づくものであれば問題ない。

**技術選定の品質は、どの製品を採用したかではなく、採用に至る判断の根拠によって評価される。**
